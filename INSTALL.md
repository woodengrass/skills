1. **Check your agent's official documentation.** Identify which coding agent is running and, if available, its version. Find out how it loads `SKILL.md` and `AGENTS.md` at both the global and project levels. If it does not load `AGENTS.md` directly, find the supported instruction filename or import method. Do not assume another agent's paths or settings apply.
2. **Ask the user what to install and where.** List `AGENTS.md` and each directory containing a `SKILL.md` under the repository's [`skill/` directory](https://github.com/woodengrass/skills/tree/main/skill) as separate choices. Add one more choice: the OpenCode V2 setup in [`opencode/`](https://github.com/woodengrass/skills/tree/main/opencode) (Mac only). Describe it in one line: it installs OpenCode V2 and Claude Code if they are missing, and replaces the current OpenCode configuration with this repository's agent roles, permissions, plugins, all of its skills, and its own `AGENTS.md`. Let the user select one or more items, including all of them if they want. In the same message, ask whether to install the other selected items globally for this agent or only in a specific project. Wait for the answers before writing files. If the project root is unclear, ask the user to specify it. If the user chose the OpenCode setup, follow step 6 for it, and do not install skills or `AGENTS.md` into OpenCode separately, because the setup already includes them.
3. **Fetch only the selected items from GitHub.** If the user chose `AGENTS.md`, fetch the [raw instructions](https://raw.githubusercontent.com/woodengrass/skills/main/AGENTS.md). For each selected skill, fetch its `SKILL.md` and any bundled files individually using their raw GitHub URLs. Do not clone the repository, download an archive of the whole repository, or ask the user to download the files manually. The OpenCode setup is the exception; see step 6.
4. **Install within the selected scope.** Put each selected skill where the agent looks for it, preserving its directory structure. If the user selected `AGENTS.md`, install it using a method the agent supports. Preserve existing instructions and settings, and ask the user before resolving any conflicts. If there is no supported installation method or you lack write access, report what you could not install. Do not switch to another scope.
5. **Verify and report.** Confirm that the files and settings are in the correct locations. If the agent provides a way to check that it loaded the instructions or skill, run that check once. Report the installation scope, the actual paths used, and whether the user needs to restart the agent or start a new session.
6. **Install the OpenCode setup, if selected.** The installer copies the setup into `~/.config/opencode`, so the clone is only needed while it runs.
   1. Check for `git`, `node`, `npm`, `npx`, and `bun` (it may be at `~/.bun/bin/bun`). If any are missing, tell the user which ones and how you would install them, and install them only after the user agrees. Run `opencode --version`. If it shows version 1, the installer stops, because this setup needs V2: tell the user, and remove V1 only after the user agrees.
   2. Clone the repository into a new temporary folder, for example one made with `mktemp -d`.
   3. Before running the installer, tell the user what it will change: if OpenCode is missing it installs the latest `@opencode/cli` globally with npm, and an installed V2 keeps its version; it installs Claude Code with its official install script if `~/.local/bin/claude` is missing, moves anything in `~/.config/opencode` that it replaces and that differs from this setup into `~/.config/opencode.backup-<time>/`, moves an old `opencode.json` there too because OpenCode would merge it with this setup's `opencode.jsonc`, adds `~/.local/bin` to `PATH` in `~/.zshrc`, and restarts the OpenCode background service. Other files in `~/.config/opencode`, such as other plugins and `service.json`, are left alone. Run it after the user agrees: `<clone>/opencode/install.sh`. It skips steps that are already done, so running it again is safe. Delete the temporary clone when it finishes.
   4. Read its output. For a plugin listed as failed, run `bun test` in that plugin's directory and show the user the failing test. If the MCP list is empty, run `opencode mcp list` again after a few seconds; the first query after a restart can come back empty.
   5. Under "不屬於這套設定的外掛", the installer lists plugins that are not part of this setup: each file or folder in `~/.config/opencode/plugins/` marked as a V2 plugin, a V1 plugin that V2 does not load, or of unknown version, and the plugins and dependencies named in the old `opencode.json` and `package.json`. Show the user this list, explain for each one what it does (read its code or its package description) and whether V2 can load it, and ask which ones to remove. Move the ones the user picks into the backup folder, unless the user asks to delete them outright. Leave the rest as they are.
   6. Signing in is the user's step. Give the user the commands from the end of the installer's output to run themselves: `~/.local/bin/claude auth login`, `opencode auth login openai`, and `opencode auth login opencode-go`.
   7. Ask whether this computer needs MCP servers of its own, such as Xcode, JetBrains, or a database. They go in a local plugin under `~/.config/opencode/plugins/`, never in the repository; [`opencode/README.md`](https://github.com/woodengrass/skills/blob/main/opencode/README.md) shows how.
   8. Report the output of `opencode --version`, the MCP list, the backup folder if one was made, the plugins removed, and what the user still needs to do. Tell the user to open a new terminal so the `PATH` change applies, and that later updates take one command: `curl -fsSL https://raw.githubusercontent.com/woodengrass/skills/main/opencode/update.sh | sh`.
